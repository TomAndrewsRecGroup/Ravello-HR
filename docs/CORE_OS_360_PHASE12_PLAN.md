# Core-OS 360 Phase 12: Compliance Digital Twin — Plan

No detailed operator brief exists in the repo for this phase — the same
situation Phases 8-11 were in. Scope is derived from the phase's own name
("Compliance Digital Twin") plus a careful audit of what the codebase
already computes, per this repo's own standing discipline (Phase 4's
existing-operations audit, Phase 8's own plan doc) of checking before
building rather than assuming.

## What "digital twin" means here, precisely

A **read-time, deterministic, consolidated model of a client's entire
compliance state** — one page that answers "what does this client's
compliance picture look like right now, across every EHS pillar", built
by ASSEMBLING the outputs of five modules this codebase already has,
never by computing a single new raw fact:

| Existing module | What it already computes |
|---|---|
| `lib/hs/kpis.ts` (`computeHsKpis`, Phase 4) | Incidents/RIDDOR/toolbox talks (12mo), last audit score + trend, equipment overdue/due-soon |
| `lib/governance/kpis.ts` (`computeGovernanceKpis`, Phase 5 Group 8) | Incident frequency rate, waste non-conformance %, objectives on-track %, overdue legal evaluations |
| `lib/riskGraph/intelligence.ts` (`computeRiskGraphIntelligence`, Phase 8) | Uncovered hazards, ineffective shared controls, assessments relying on ineffective controls, unlinked legal obligations |
| `lib/incidentPatterns/analyze.ts` (`analyzeIncidentPatterns`, Phase 10) | Incident type breakdown, recurring confirmed root causes, site/department clusters, severity trend vs. prior window |
| `lib/evidenceEngine/analyze.ts` (`analyzeEvidenceCoverage`, Phase 11) | Register-completion evidence coverage % and gaps |

**This phase adds no new raw computation of its own.** It adds exactly
one thing none of the five modules above provide on their own: a
**per-area RAG (red/amber/green) status**, derived by fixed, documented,
inspectable numeric thresholds — mirroring `lib/health/scoring.ts`'s own
`computeBand()` shape (an early-return `if` chain over named thresholds,
not a formula) — plus one **overall** status (the worst of the five
areas). Every "reason" attached to a status is a deterministic sentence
built directly from the same numbers already computed elsewhere — never
an AI narrative, never a summary generated by a model.

## Absolute rules this phase holds to (this codebase's own standing ones)

- **No predictive/AI scoring, anywhere** — the same rule Phase 10's own
  plan stated explicitly. A RAG band is a plain threshold comparison on
  numbers that already exist; it reports what has ALREADY happened
  (an overdue inspection count, a confirmed root cause, an evidence gap),
  never a probability or a "likely to recur" framing.
- **No stored snapshot.** Computed at read time from the same live
  Supabase reads each of the five source pages already makes — no new
  table, nothing that can drift out of sync with the rows it summarises,
  the exact posture `lib/health/scoring.ts`/`lib/hs/kpis.ts`/
  `lib/governance/kpis.ts` already take.
- **No new migration.** This is entirely TypeScript over data the
  existing five modules already read — the same situation Phases 9, 10
  and 11 were in (each shipped with no migration at all).
- **REUSE, never a parallel system.** Every underlying fact is read
  through the EXISTING pure function for that fact — this phase never
  re-implements "is this audit score low" or "is this hazard uncovered"
  a second time. The assembly module's only new logic is the banding
  thresholds and the combination into one structure.
- **Thresholds are reused where one already exists in this codebase**,
  not invented twice: the 70%-audit-score threshold and the
  "current-window major severity worsening vs. prior" comparison both
  echo the Phase 5 Group 6 management-review data pack's own established
  practice ("audits scoring below a fixed 70% threshold").

## What this phase deliberately does NOT do

- **No new capability, no new RLS, no new table.** Pure assembly + one
  admin page + one read-only portal page, gated exactly like every
  other Phase 8-11 page (`risk.read`/staff on admin; `protect` alone on
  portal, since "nothing here is self-certified").
- **No cross-client rollup / consultancy-portfolio view.** Single-client
  scope, the same explicit decision Phase 8's plan made for the Risk
  Graph — this deepens a single tenant's own picture rather than
  reaching across the Phase 6/7 consultancy model.
- **No export/PDF.** The Value Report (Phase 5 Group 8) already exists
  for a printable monthly artefact; this phase is a live dashboard, not
  a second report generator.
- **No "improvement over time" trend line beyond what the source modules
  already carry** (the audit-score trend and the incident severity
  window comparison are the only "then vs. now" comparisons any of the
  five source modules make, and both are reused as-is).
- **No board-level narrative or executive summary** — that is Phase 13
  (Board Assurance & Executive Reporting), a different phase with its
  own name in the task list; conflating the two here would be scope
  creep into work explicitly reserved for next.

## Delivery groups

1. **Group 1 — the assembly module.** `lib/complianceTwin/assemble.ts`
   (shared-dupe pair): `assembleComplianceTwin()`, pure, taking the
   five modules' own already-computed output types as its input (never
   re-fetching or re-deriving), returning one `ComplianceTwinSnapshot`
   with five `ComplianceTwinArea` entries plus an overall band. Full
   unit test coverage, including the threshold boundaries and the
   worst-of-five combination.
2. **Group 2 — UI.** Admin: a 29th `HsCompanyTabs.tsx` tab,
   `/health-safety/<companyId>/digital-twin`, reusing each source page's
   own existing data-fetch shape (the five reads this page needs are the
   same reads their own five existing pages already make — no new query
   shape invented). Portal: read-only `/protect/digital-twin`, gated by
   `protect` alone.
3. **Group 3 — regression, adversarial QA, handover.** The same
   discipline every prior phase's final group has followed: re-run every
   suite, sweep for a real defect with fresh eyes, document design
   decisions rather than leaving them implicit, write
   `docs/CORE_OS_360_PHASE12_HANDOVER.md` with an honest gate verdict.

**Phase 13 is not to begin** until this phase is merged and deployed,
per the operator's standing instruction.
